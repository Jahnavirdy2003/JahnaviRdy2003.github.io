THE FEATURED CASE STUDY

From a single item
to a complete outfit.

Finding visually similar clothes is only part of the problem. A useful outfit recommender also needs descriptions, complementary categories, and a way to reason about whether items belong together.

My documented contribution

Built the text-search experience and helped merge it with the outfit-scoring flow into one Streamlit application. The repository attributes text search to Jahnavi Reddy Poddutoori and the outfit scorer to Kishan.

01 / Model architecture+

EfficientNet-B0 converts each 224 × 224 image into 1,280 visual features; a trainable projection maps these to 256 dimensions. Frozen Sentence-BERT (all-MiniLM-L6-v2) produces 384-dimensional text features, followed by a trainable 256-dimensional projection.

ImageEfficientNet-B0 → 256-D
DescriptionSentence-BERT → 256-D
FusionElement-wise addition + LayerNorm
Compatibility|embedding A − embedding B| → MLP (256 → 128 → 1) → sigmoid

Training learns a pairwise compatibility score. Recommendation ranks cached catalog embeddings by cosine similarity, then uses category-aware outfit assembly. These are distinct scoring paths.

02 / Data and training+

Uses Marqo/Polyvore fashion images, descriptions, and outfit membership. Items in the same outfit form positive pairs; items outside that outfit form negative pairs. The loader supports consecutive pairs, all within-outfit pairs, and category-matched hard negatives.

Images are resized to 224 × 224, normalized with ImageNet statistics, and augmented with horizontal flips and color jitter for training. The loader splits outfit IDs 90/10. Negative candidates come from the full catalog, so this should not be presented as a strictly item-disjoint test.

The experiment runner varies data caps, backbone freezing, learning rate, dropout, weight decay, and pair generation; it records metrics, curves, configuration, and the best checkpoint.

04 / Application and next steps+

The Streamlit application supports uploaded images, camera input, text search, and an outfit scorer for 2–6 items. Shared outfit-building functions fill complementary clothing categories and avoid duplicate selections. Models and catalog data are cached for reuse.

Text-only queries are less reliable than combined image-and-text inputs. The static catalog must be rebuilt for new items, and the training documentation reports overfitting. Next steps include stronger split isolation, repeated evaluation, and better alignment between retrieval and compatibility scoring.

Model checkpoints and catalog embeddings are not bundled in GitHub. The repository contains local run instructions; a public fashion-app deployment is not linked.

Say Cheese!

A face-recognition attendance application that connects camera capture, identity matching, and daily records in a Flask interface.

FlaskMTCNNFaceNetMySQLOpenCV
Approach, results & limitations+

Recognition pipeline

MTCNN detects faces. A VGGFace2-pretrained Inception-ResNet-V1 generates 512-dimensional face embeddings. The system compares embeddings by cosine similarity and accepts the best match at a configured threshold of 0.6.

From recognition to records

Supports camera and photo registration, user management, attendance history, and CSV export. MySQL stores user, embedding, and attendance records; a CSV fallback supports attendance retrieval during database failures. Duplicate daily attendance checks connect model output to usable records.

Engineering considerations

The backend selects CUDA when available and includes database retries and connection management. The recognition threshold is a configuration choice, not a demonstrated accuracy result; this repository does not publish a labeled test-set benchmark.

Task scheduling, measured

A Python and Streamlit task manager comparing merge, heap, and bucket-based sorting by priority, deadline, and duration.

PythonStreamlitMerge sortHeapBenchmarking
Approach, results & limitations+

Implementation

Uses recursive merge sort, heap-based sorting with custom comparisons, and a bucket-based approach tuned to bounded task attributes. Priority has five possible values; deadline buckets follow the date range; duration uses 15-minute buckets.

Recorded benchmark

For 1,000 tasks sorted by priority, the committed CSV reports average times over 10 trials: merge 1.481 ms, heap 1.156 ms, and bucket 0.077 ms—about 19× faster than merge in that workload.

This is a workload-specific result, not a universal speed claim. Bucket sorting benefits from a compact key range, and duration buckets group values into intervals.
